# AI Agent 工序卡（S0–S11）

> 创建日期: 2026-07-26
>
> **每道工序开工前读对应那张卡。** 每张卡三段：
> **① 动作清单**（照做，逐条）· **② 退出判定**（自问，全"是"才准进下一道）·
> **③ 常见偷懒模式**（你最可能在这道犯的错——先自查再动手）。
>
> 通则：`<SKILL_DIR>` = 本 skill 的安装目录。开工先解析一次：
> ```bash
> SKILL_DIR="$(ls -d ./.claude/skills/pact ~/.claude/skills/pact 2>/dev/null | head -1)"
> ```

---

## 每一轮都要做的三件事

无论在哪道工序，每一轮回复都照做：

1. **读** `.pact/board.md` → 我在第几道？上轮做到哪？有无阻塞？
2. **只做当前这一道** → 不提前、不回头。
3. **写** `.pact/board.md` → 更新工序状态 + 本轮做了什么 + 下一道 + 阻塞。

> 上下文会被压缩，**你的记忆不可信，落盘的文件才可信**。
> `board.md` 没更新 = 这一轮不算做完。

---

## S0 · 定位与摄入

### 动作清单
1. 探测：`ls` 项目根；有没有 `src/`、`backend/`、`apps/` 且非空？有没有 `PACT.md`？
   `$ARGUMENTS` 指向的是文档还是一句想法？
2. 定模式（`--new` / `--feature` / `--merge` / `--build` / `--audit`），
   **开场第一句就说明判定结果与依据**，别闷头开工。
3. 读全部给定物料。存量项目**必须读实际代码**，不能只读文档。
4. 建 `.pact/`，从 `<SKILL_DIR>/templates/` 拷起步文件。`board.md` 必须含工序状态表。
5. `PACT.md` 从 `<SKILL_DIR>/templates/PACT.md` 拷，头部填 `创建日期`（当前实际日期）。
6. 物料归位（若既有文档散落在外）：**先 grep 查引用 → 移动 → 改引用 → 跑构建/测试验证**。

### 退出判定
- [ ] 模式已判定，且我已向用户说明依据
- [ ] `.pact/` 骨架文件齐备且非空
- [ ] `PACT.md` 头部创建日期已填（真实日期，不是占位符）
- [ ] `board.md` 工序状态表已建，S0 标「已完成」

### 常见偷懒模式
- ❌ **不判模式直接开写**——结果给存量项目写了一份 greenfield 规格，全是错的。
- ❌ **只读文档不读代码**——文档说的能力可能根本没实现，或已改名。**运行代码才是事实来源。**
- ❌ **不查引用就 `mv` 物料**——有过教训：验收样本包被 10 个源文件以 `../../docs/` 引用，
  直接移动导致 88 个测试全断。四步走不能省。
- ❌ 创建日期填 `<YYYY-MM-DD>` 占位符——lint 会拦，但更糟的是你可能忘了回来填。

## S1 · 访谈门

### 动作清单
1. 打开 `.pact/interview.md`，**十二类逐项过**（交付形态 / 用户角色 / 核心场景 / 规模性能 /
   数据持久化 / 集成依赖 / 权限合规 / **非目标** / 成功定义 / 约束 / 视觉交互 / 既有资产）。
2. 每类判定：`已答`（用户已说）/ `阻塞`（猜错代价大）/ `可假设`（取默认+标注）。
3. 所有 `阻塞` 项**一次性批量** `AskUserQuestion`，每问 2–4 个候选含推荐项。
4. narration 写 `needs input:` 一行说明缺什么。
5. `可假设` 项：取默认值，写进 PACT 时标 `假设：<值>（未经确认）`。

### 退出判定
- [ ] 十二类**每一类**都有结论（不是只挑了容易的几类）
- [ ] 无 `阻塞` 状态残留
- [ ] 所有假设都已显式标注，没有藏在心里的默认值

### 常见偷懒模式
- ❌ **跳过访谈直接写规格**——这是本流程最常见也最贵的错。产出的 PACT 会把你自己的
  默认假设伪装成用户需求，用户读的时候以为是自己说的。
- ❌ **一个一个挤牙膏地问**——用户要回答 8 次。批量问，一次问完。
- ❌ **跳过第 8 类「非目标」**——最容易漏、代价最大。范围膨胀总是从「这个顺手也做了吧」开始。
- ❌ **什么都问**——猜错代价小的（比如日志格式）就取默认+标注，别浪费用户的往返。

## S2 · 熔合门（条件工序）

### 触发判定
物料 ≥2 份（PRD + SDD、文档 + 存量代码、新需求 + 旧约定…）→ **必做**。
只有一份来源 → `board.md` 标 `已跳过（只有一份来源，无差异可裁）`。

### 动作清单
1. 建立来源清单（来源 ID / 文件 / 类型 / 日期 / 可信度）。
2. 逐条比对，凡说法不一致的记一条 `DIFF-ID`，分类为：**矛盾 / 细化 / 缺漏 / 越界**。
3. 每条给「建议」（按默认优先级：运行代码 > SDD > 原型 > PRD > 历史文档）。
4. **矛盾类和高影响项批量 `AskUserQuestion`** 让用户裁定。
5. 裁定结论：① 写进 PACT 正文（不留"两种说法"）② **非平凡的落一条 `A5` D-ID，
   落选方案写进「已否决」**。

### 退出判定
- [ ] 全部 `DIFF` 状态 = 已裁定
- [ ] 每条非平凡裁定在 `A5` 有对应 D-ID，且「已否决」写了落选方案与理由
- [ ] PACT 正文里搜不到"两种说法并存"的残留

### 常见偷懒模式
- ❌ **自己"择优采用"**——「SDD 更精准所以采 SDD」。**「更精准」≠「自动覆盖」**。
  矛盾类必须用户裁定，这是硬规矩。
- ❌ **裁定了但不落 D-ID**——三个月后没人知道为什么选了这个，也不知道否决过什么。
- ❌ **只比对文档，不比对代码**——存量代码是最高优先级的来源，它跟文档打架时最需要裁定。

## S3 · 存量代码八维评估（条件工序 · 只读不改码）

### 触发判定
有实质代码 → **必做**。空项目 → `board.md` 标 `已跳过（空项目，无存量代码）`。

### 动作清单
1. 实现盘点：模块 / 语言框架 / 规模 / 职责 / 与本次需求的关联点。
2. 八维逐项评，**每维必须给证据 `file:line`**，标严重度 P0–P2：
   ① 结构与分层 ② 核心不变量 ③ 既有约定在代码里是否被遵守 ④ 数据正确性铁律
   ⑤ 安全与权限 ⑥ 可维护性与技术债 ⑦ 性能与可扩展 ⑧ 测试与文档
3. 结论**回流到 PACT**：现状约束 → `P7`；结构 → `A2`；P0 → `T5` 的 M0；
   与新需求冲突的存量设计 → `A5` D-ID。
4. **全程只读，一行代码都不改。**

### 退出判定
- [ ] 八维**全部**评完（不是挑了三四维）
- [ ] 每个问题都有 `file:line` 证据，不是"感觉有点乱"
- [ ] 结论已回流到 PACT 对应锚点（不是只躺在 assessment.md 里）
- [ ] P0 已排进 `T5` 的 M0

### 常见偷懒模式
- ❌ **评估完就开始重写**——本工序的目的是**摸清现状让 PACT 接得上**，不是推倒重来。
- ❌ **无证据的判断**——「代码质量一般」不是评估，`file:line` + 具体问题才是。
- ❌ **把「结构整理」降级为 P2**——散落文件、文档与实际不符属 **P1（影响可接手性）**，
  必须本轮处理，不得推迟。
- ❌ **评估结论不回流**——写了一份漂亮报告，PACT 里却看不出任何存量约束的痕迹。

## S4 · 写 P 层

### 动作清单
1. 逐节写 `P1–P8`，边写边对照 `<SKILL_DIR>/references/authoring-guide.md` 的精度标准。
2. `P5` 需求清单：逐句扫描所有来源，**含「且/或/除非/当…时」的必须拆成多条**。
3. **横切项清单逐一过**：权限/校验/边界/空状态/错误/幂等并发/破坏性二次确认/
   分页性能/审计日志/国际化。不需要的显式写「本项目不需要，因为…」。
4. 写覆盖声明：「来源 X 全文 N 段已全部归类，无遗漏」。

### 退出判定
- [ ] `P5` 每条描述**可判真假**、验收标准**可量化**
- [ ] 横切项清单**每一项**都打勾或写了「不需要 + 理由」
- [ ] `P6` 非目标**非空**，且每条有「为什么不做」
- [ ] `P8` 全是数字或可执行判定，没有「好用」「稳定」
- [ ] 覆盖声明已写

### 常见偷懒模式
- ❌ **`P6` 留空或只写一句「其他不做」**——范围失控的起点。
- ❌ **一条需求塞多个条件**——「支持导出且需要权限校验」应拆成两条，否则验收无法判定。
- ❌ **横切项整块跳过**——权限、空状态、错误处理是最容易在实现期才发现漏了的。
- ❌ **`P2` 背景写成一句「为了提升效率」**——后人遇到没写到的取舍时无从判断该往哪边倒。

---

## S5 · 写 A 层

### 动作清单
1. `A1` 边界：**明确写出「不负责什么」**，每个外部依赖注明**失效时的行为**。
2. `A2` 结构：目录树 + 每格职责 + 关联 R-ID。
3. `A3` 链路：端到端，标出**权限在哪一跳裁定**。
4. `A4` 原则：具体到能据以驳回一个 PR。
5. `A5` 决策：每条四件套 **选项 / 结论 / 理由 / 已否决**。

### 退出判定
- [ ] 每个非平凡取舍都有 D-ID（技术选型、数据模型取舍、S2 的每条裁定、与存量冲突的处置）
- [ ] 每条 D-ID 的「理由」**能被反驳**（不是「更现代/更好/社区活跃」）
- [ ] 每条 D-ID 的「已否决」写了**落选方案 + 否决理由**
- [ ] `A2` 能让一个新人知道「我写的这段代码该放哪」

### 常见偷懒模式
- ❌ **理由写万金油**——「更现代、社区活跃、性能更好」对任何选型都成立，等于没写。
  好理由长这样：「团队三人全部熟悉 Vue，既有管理端已是 Vue 3，共用组件库可省约两周；
  性能不是瓶颈（P8 阈值很宽）」。
- ❌ **只记结论不记否决**——这是 PACT 区别于 SDD 的关键。后人要看到**路口**，不只是结果。
- ❌ **推翻旧决策时直接删掉**——应新增 D-ID 说明为什么推翻，旧的标 `已被 D0xx 取代`。
- ❌ **`A2` 出现 `utils/`、`common/`、`helpers/` 万能桶**——说明职责没想清楚。

---

## S6 · 写 C 层 ← 精度门槛在这里

### 动作清单
1. 逐节写 `C1–C11`。**每条契约要么是表格，要么是代码块/schema。**
2. `C1`：字段的 名称·类型·可空·默认值·含义 齐全 + 索引 + 关联 + 历史数据兼容策略。
3. `C2`：状态机给 `状态 × 事件` **全表**，含 `✗` 非法格 + 非法迁移的处理方式。
4. `C4`：给**真实的请求/响应示例**，不是"返回用户信息"。
5. `C8`：写清**服务端在哪一行做裁定**、空范围行为、越权行为。
6. 不适用的条目写 `N/A（具体理由）`，**不要删锚点、不要留空**。

### 退出判定
- [ ] 全文搜不到「到时候再定」「按需处理」「视情况而定」
- [ ] `C1`/`C4` 都是表格或代码块（lint 会查这两个）
- [ ] `C2` 状态机是全表，能看出「没画的那条线」是禁止还是遗漏
- [ ] `C8` 写明了服务端裁定点的具体位置
- [ ] 所有 `N/A` 都带了具体理由

### 常见偷懒模式
- ❌ **散文式契约**——「接口应返回用户信息并做好错误处理」。实现者读完还得自己设计，
  这就是没写够。lint 会拦 `C1`/`C4`，但其余条目要靠你自觉。
- ❌ **字段只列名字**——可空性和默认值缺失会直接导致实现者猜。
- ❌ **状态机只画箭头图**——图里看不出未画的迁移是禁止还是遗漏。
- ❌ **`N/A` 不写理由**——「C11: N/A」不够，要写「N/A（本功能不涉及任何模型调用）」。
- ❌ **把决策推给实现者**——C 层的判定标准是「实现者不需要再做任何设计决策，只需要打字」。

## S7 · 写 T 层

### 动作清单
1. `T1`：**从 `P5` 抄出每一个 R-ID**，逐行给验收方式（测试名/命令/操作步骤）。
2. `T2`：每项指标给数字 + 测量方式。
3. `T3`：写客观可判定的停工线。通用五条 + 项目特有的。
4. `T4`：可勾选的 DoD 清单。
5. `T5`：每个里程碑给 R-ID 清单、出口条件、**明确不含什么**。
6. **估算门**（需对外报价/排期时必做，否则 `board.md` 标「已跳过（理由）」）：
   照 `references/effort-estimation.md` 走。**算术交给工具，别手算**：
   `cp templates/rate-card.json .pact/`（改成执行者实测费率）→
   `bash scripts/pact-estimate.sh PACT.md`（自动分层、套卡、出 `.pact/estimate-calc.md`）。
   再把三条线写回 `T5`、停工线写回 `T3`、工期与团队写回 `P7`，
   对外承诺用手写的 `.pact/estimate.md`（完整格式：前提/假设/阻塞源/停工线）。
   工具会强制 S1 停止条件（缺 `T1` 验收即拒绝出数）。

### 退出判定
- [ ] `P5` 的**每一个** R-ID 在 `T1` 都有一行（跑 lint 会查这条）
- [ ] 验收方式具体到能执行，没有「手工测试」「检查是否正常」
- [ ] `T3` 停工线非空且客观可判定
- [ ] `T5` 每个里程碑都有「明确不含」
- [ ] **估算门已过（`.pact/estimate.md` 在）或已标「已跳过（理由）」**

### 常见偷懒模式
- ❌ **验收写「手工测试」**——不可执行、不可回归，等于没有验收。
- ❌ **漏掉部分 R-ID**——lint 会抓，但漏的往往正是最难验收的那几条（权限、边界）。
- ❌ **停工线写「出现严重问题时停止」**——什么算严重？要客观可判定。
- ❌ **里程碑不写「明确不含」**——里程碑会无声膨胀，永远做不完。
- ❌ **在 `P7` 直接填「工期约 X 个月、团队 Y 人」当假设**——这是拍脑袋数字，
  一旦进合同就是承诺。lint 第 10 项会 WARN。要么走估算门，要么别写。
- ❌ **因为 PACT 写得好就下调工期**——规格提高的是方向正确率与验收清晰度，
  **不是 AI 骨架覆盖率**（恒定约 50%）。时间预算必须显性留给后 50%。

## S8 · 完备性门 ← 硬闸门

> **冷读门必查一项：过度设计。** 逐个 C 层契约问「这是哪条 R-ID 要的」——
> 反查不到的字段/表/抽象/约束就是野生设计，删掉或回 `P5` 补需求。
> 约束是否被无授权扩面（需求说「A」写成「A/B/C」）尤其要查，这是最隐蔽的一类。

### 动作清单
1. **跑 lint**：`bash <SKILL_DIR>/scripts/pact-lint.sh PACT.md --level=<full|feature>`，
   **档位必须与 `PACT.md` 头部「完备度档位」一致**（新建项目 full，大需求 feature）。FAIL 逐项修到 PASS。
2. **反扫**：拿全部输入物料反向对照 PACT，列 未覆盖/部分覆盖/偏离。
3. **冷读门**：用 `Agent` 工具（`subagent_type: general-purpose`）另起一个**全新** agent，
   **只给它 `PACT.md` 的绝对路径**，prompt 见 `<SKILL_DIR>/templates/cold-read.md`。
4. 判定并把报告追加到 `.pact/cold-read.md`：
   - 追问清单为空 + 计划与意图一致 → **PASS**
   - 它问的答案其实在文里 → 表述不可发现，调结构后**重跑**
   - 它必须追问背景/意图/约束 → **FAIL**，回填后**重跑**
   - 它的实现计划跑偏 → **FAIL**，`P4/P5/P6` 有歧义，改写后**重跑**
5. **跑到 PASS 为止。**

### 退出判定
- [ ] `pact-lint.sh` exit code = 0（真跑了，贴了结果）
- [ ] 反扫结论已写，未覆盖项已补
- [ ] 冷读门 PASS，且报告已落盘 `.pact/cold-read.md`

### 常见偷懒模式
- ❌ **不跑冷读门直接冻结**——这是 PACT 的**定义性检验**，跳过它 PACT 就退化成普通 SDD。
- ❌ **冷读 FAIL 了但觉得"问题不大"**——它必须追问的每一个问题，都是真实的规格漏洞。
- ❌ **给冷读 agent 额外上下文**——给了就失去意义了。只给 `PACT.md` 路径，别的什么都不给。
- ❌ **lint FAIL 了改 lint 而不是改文档**——同 T3 停工线的精神：不为通过而放宽标准。

## S9 · 冻结

### 动作清单
1. `PACT.md` 头部改 `状态: 已冻结 · <日期>`。
2. 建 `.pact/changelog.md`。
3. `board.md` 记「S8 三道门全过，已冻结」。

### 退出判定
- [ ] 头部状态已改（`pact-status.sh` 会核对）
- [ ] changelog 已建
- [ ] board 已记录

### 常见偷懒模式
- ❌ **冻结后改规格不记 changelog**——规格漂移是最贵的债。
- ❌ **改了 `P1/P2/P4/P5/P6` 却不重跑冷读门**——意图与范围层变了，冷读结论就失效了。

## S10 · 施工 LOOP

### 动作清单（每个工作单元一轮）
1. 从 `T5` 按里程碑顺序取下一个未完成单元（**P0 全清前不碰打磨项**）。
2. 实现：代码落到 `A2` 约定位置，配置进 `C7` 集中层。
   **每段业务代码必须带标注** `// @pact R001`（多个写 `// @pact R001,R002`；
   Python/Shell 用 `#`，模板用 `<!-- -->`）。没标注 = `pact-trace.sh` 反查不到 = 不算实现。
3. 验收：跑 `T1` 指定的验收方式；有 UI 追加 token-lint / visual-diff / computed-style；
   核对 `C3` 相关不变量。
4. 判定：任一 FAIL → **同一单元继续修，不前进**；全过 → `coverage.md` 标 `已验证`。
5. 对照 `T3` 检查停工线。
6. **跑 `bash <SKILL_DIR>/scripts/pact-trace.sh`** —— 确认本轮 R-ID 已在代码里可反查，
   且无虚报、无野生 R-ID。
7. 更新 `coverage.md` 与 `board.md`。

### 用户中途改需求 → 走 S10-CR 五步（不要直接改代码）
1. 回 `P5` 加/改 R-ID（新号，不复用已删的号；若与 `P6` 非目标冲突则一并更新）
2. 回 `T1` 补可执行验收
3. 影响契约就同步改 `C` 层
4. 记 `.pact/changelog.md`（改了什么 / **为什么** / 影响哪些 R-ID）
5. 改到 `P1/P2/P4/P5/P6` → **重跑 S8 冷读门**；只改 C 层细节 → 跑 lint 即可；
   推翻了决策 → `A5` 新增 D-ID，旧的标 `已被 D0xx 取代`，不要删

> 变更超出当前里程碑 → 回 `T5` 排后续里程碑，**不要塞进正在做的单元**。
> 变更与 `P6` 非目标或 `P7` 硬约束冲突 → 停下来问用户，不要自行放宽约束。

### 退出判定
- [ ] `coverage.md` 全部 R-ID = `已验证`
- [ ] `C3` 不变量检查通过
- [ ] 无未处理的停工线命中
- [ ] 本轮所有需求变更都走完了 S10-CR 五步
- [ ] `pact-trace.sh --require-complete` 通过（每个 R-ID 都能在代码里反查到）

### 常见偷懒模式
- ❌ **写没有 R-ID 的功能**——要加功能先回 `P5` 加条目、`T1` 加验收、记 changelog。
- ❌ **单元没过就前进**——攒着一堆半成品，最后一起 debug。
- ❌ **改宽断言让测试通过**——`T3` 停工线，命中即停。失败先查根因。
- ❌ **只跑改动相关的测试**——收尾前必须跑全量。
- ❌ **忘了更新 `coverage.md`**——最后无法判断到底做完没有。
- ❌ **用户说「顺手加个 X」就直接写**——绕过规格改代码，PACT 立刻退化成过时的摆设文档。
  必须走 S10-CR 五步。这是冻结后最容易破防的地方。
- ❌ **写了代码不加 `@pact` 标注**——覆盖表就成了无法核对的自说自话。`pact-trace.sh` 会抓。
- ❌ **在 `coverage.md` 标「已验证」但代码里没有对应标注**——这叫**虚报**，
  是 `pact-trace.sh` 的头号 FAIL。要么补标注，要么把状态改回实情。

## S11 · 收尾自检门

### 动作清单
1. `coverage.md` 全绿核对；`T1` 每条**真跑过并贴结果**。
2. PACT 反向重扫实现，列 未覆盖/部分覆盖/偏离。
3. `T2` 指标达阈值。
4. `T4` DoD 逐条打勾。
5. 规格与实现一致性核对（表结构/接口/错误码/配置 vs 代码实测）。
6. **四道机检**：`pact-status.sh` + `pact-lint.sh` + `pact-trace.sh --require-complete`
   + `pact-book.sh --check`（知识库须已按最终 `PACT.md` 重生成），贴结果。
7. 可接手性自检：`A2` 与实际目录一致 · `.env.example` 齐备 · 根目录干净 · 无 `TODO` 占位。
8. **末次冷读**：确认 PACT 描述的仍是**现在的系统**。
9. 全绿 → `result:` 一行。

### 退出判定
- [ ] 1–8 全部满足，且每项都是**真跑过**而非推断

### 常见偷懒模式
- ❌ **自称完成而没跑机检**——协议四，两个脚本必须真跑并贴结果。
- ❌ **只核对文档不核对代码**——PACT 说接口返回 `total`，代码实际返回 `count`，这类漂移最常见。
- ❌ **跳过末次冷读**——施工过程中规格常被悄悄改动，末次冷读是防漂移的最后一关。
- ❌ **报喜不报忧**——有跳过的、没做完的、降级处理的，必须在 `result:` 之外明确说出来。

## 附：状态词汇表（`board.md` 工序表只许用这四个）

| 状态 | 含义 |
|---|---|
| `未开始` | 还没轮到 |
